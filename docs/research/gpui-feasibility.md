# Research: Rust + GPUI feasibility and current blockers for Mado Mail

## Summary

GPUI is a hard requirement: current upstream docs show a standalone Windows-app path, but leave the target PC’s graphics floor and successful runtime unverified. The clear migration gate is replacing the existing OAuth OOB flow; testing-mode refresh-token expiry is a usability caveat, not a bar to personal sign-in. Neither Rust nor GPUI guarantees the memory or speed goals: matched release measurements are required.

## Findings

1. **Claim — Standalone Windows GPUI is a supported path; actual hardware compatibility is unknown.** GPUI documents a standalone `Application` and Windows Win32/DirectWrite support without GPUI platform feature flags; its framework page lists DirectX 11 rendering. GPUI is pre-1.0, often breaking across versions, and asks for latest stable Rust; the current `gpui` manifest identifies v0.2.2, Apache-2.0. **Status:** conditional blocker only if the target cannot initialize GPUI’s renderer; no documented minimum Windows version, GPU feature level, driver, or fallback was found, so no particular PC can yet be ruled in or out. The GPUI Component source describes reusable input state but its workspace pins GPUI pre-release crates exactly (`gpui-pre` 0.3.7) and warns about API mismatch from moving snapshots; do not mix arbitrary GPUI/component revisions. The full Zed Windows build guide lists MSVC/SDK/CMake requirements for building Zed, not a verified standalone-GPUI minimum. **Smallest experiment:** get the operator’s Windows version/GPU/driver, pin a compatible GPUI stack, and launch a minimal window on that machine. **Sources:** [GPUI README](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md), [GPUI manifest](https://github.com/zed-industries/zed/blob/main/crates/gpui/Cargo.toml), [GPUI examples/platform page](https://gpui.rs/examples/), [GPUI Component architecture](https://github.com/longbridge/gpui-kit/blob/main/docs/ARCHITECTURE.md), [GPUI Component workspace pins](https://github.com/longbridge/gpui-kit/blob/main/Cargo.toml), [Zed Windows build guide](https://github.com/zed-industries/zed/blob/main/docs/src/development/windows.md). **Support:** direct evidence; hardware implication is inference. **Confidence:** high for standalone support/status/license, low for hardware floor.

2. **Claim — GPUI has the primitives, but Windows editing/accessibility fidelity needs an app-level proof.** GPUI examples use actions/key bindings; GPUI Component documents Input/textarea state with selection, IME, clipboard, focus, and native text-content integration “where supported.” GPUI uses AccessKit, but developers must give custom controls accessible semantics; this is not automatic. **Status:** implementation work/unverified risk, not a confirmed incompatibility. Reuse the component input if its pinned API fits; otherwise implementing custom text fields and semantic controls adds work that can undermine the small rewrite’s schedule. **Smallest experiment:** use the production filter/rule fields and triage buttons in a Windows prototype; test Ctrl+A/C/V/X, standard navigation/selection, clipboard, IME composition, focus order, and the target screen reader. **Sources:** [GPUI README/accessibility](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md), [GPUI Component architecture](https://github.com/longbridge/gpui-kit/blob/main/docs/ARCHITECTURE.md). **Support:** direct evidence plus inference. **Confidence:** medium; no Windows interaction test performed.

3. **Claim — Current OAuth code is blocked by OOB policy, but supported personal desktop sign-in exists.** Google’s installed-app docs prescribe the system browser and a loopback listener (`127.0.0.1`/`::1`) for Windows desktop, recommend PKCE, and say the OOB redirect is deprecated/no longer supported. The repo’s `src/main/gmail.ts` uses `urn:ietf:wg:oauth:2.0:oob`, so that flow must be replaced; use fresh sign-in as scoped. Google classifies `gmail.modify` as restricted; its scope table describes read/compose/send access and says it does not allow immediate permanent deletion. The existing app uses it for Inbox reading and message changes. Google exempts personal-use apps—only you or a few personally known users—from verification submission, while Testing requires listed test users and displays an unverified-app warning. External Testing refresh tokens expire after 7 days for Gmail scopes; tokens can also be revoked or invalidated for other documented reasons. **Status:** OOB is a confirmed blocker; personal sign-in is feasible with a supported flow, subject to consent/account policy. Testing expiry is a conditional operational blocker only if weekly reauthorization is unacceptable; it is not proof the user cannot authenticate. Keep the refresh token separately in OS-protected credential storage and out of settings exports/logs; an installed app’s embedded client secret is not a secret. **Separate behavior gate:** `src/main/gmail.ts` currently removes `UNREAD` in both archive and trash handlers, contrary to the preserved-unread goal; fix and test this during implementation. **Smallest experiment:** create/use a Desktop OAuth client, add the account as a tester if Testing, complete loopback + PKCE fresh sign-in, and verify token refresh behavior without touching production mail. **Sources:** [Google desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [OAuth refresh-token rules](https://developers.google.com/identity/protocols/oauth2), [verification exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [repo Gmail implementation](../../src/main/gmail.ts). **Support:** direct evidence; storage recommendation is inference. **Confidence:** high.

4. **Claim — Performance must be measured against Electron as a whole, not inferred from the framework.** Electron documents separate main, renderer, GPU, and utility processes; its process metrics expose per-process type, CPU, and memory. Compare the entire app-owned Electron process tree with the GPUI process, plus per-process CPU/private committed memory and dedicated/shared GPU memory where Windows exposes it. **Status:** no performance blocker is established, but success is unverified and has no numeric target yet. Build both in release mode on the same identified PC, with the same window/layout and a deterministic 400-message dataset; repeat cold launch-to-interactive, filter/selection/preview/staging keyboard workflows, idle/peak memory, and a short soak. Report medians and p95 latency, summed private memory, CPU over fixed intervals, and GPU memory separately; keep network/Gmail write time out of UI timings or report it separately. Set an improvement threshold before claiming success. **Smallest experiment:** capture Electron baseline measurements first, then rerun the same script on the release GPUI build. **Sources:** [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Electron ProcessMetric](https://www.electronjs.org/docs/latest/api/structures/process-metric). **Support:** direct evidence for measurement surface; benchmark design is recommendation. **Confidence:** high on need for matched measurement, none on outcome.

## Contradictions

GPUI’s framework examples page says Windows rendering uses DirectX 11, while Zed’s Windows build guide says the Zed application currently uses Vulkan. These are different layers/products and do not establish which path a pinned standalone app will use; GPUI has not stated a minimum GPU/driver requirement in the sources reviewed. Resolve with the exact GPUI revision and the operator’s PC, not by transferring Zed’s application requirements to GPUI.

## Missing evidence

- Target PC’s Windows release, GPU model, driver, and hardware acceleration state; no actual GPUI launch test.
- A quantitative speed/memory improvement threshold and measured Electron baseline.
- Windows IME, editing shortcuts, clipboard, accessibility/screen-reader behavior for this layout.
- A final compatible GPUI/component revision and full transitive dependency-license audit; GPUI core declares Apache-2.0.
- Cloud OAuth project publishing status/test-user setup cannot be inferred; no credentials or token files were inspected.

No builds, measurements, authentication, Gmail actions, or credential reads were performed.

## Next steps

Confirm the target PC and numeric success threshold; then prototype one pinned GPUI window/input on that machine and establish the Electron release baseline before implementation claims are made. Replace OOB with desktop loopback + PKCE, decide Testing versus Production based on refresh-token cadence, and preserve unread in archive/trash.
